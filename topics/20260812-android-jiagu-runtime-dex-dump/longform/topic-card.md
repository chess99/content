# 选题卡　静态反编译只剩 StubApp，我怎样从运行中的加固 APK 抓回业务 DEX

## 核心洞察

动态拆壳的价值不止是让 JADX 多吐出一批类。本次从运行时内存恢复业务 DEX 后，源码里的触摸分区和状态机直接纠正了黑盒复刻对核心交互的误判。

## 目标读者

做过 APK 静态分析，了解 ADB、DEX 和 JADX，希望交流运行时拆壳排障方法的 Android 逆向研究者。

## 核心论点

1. Manifest、壳 so 和静态 JADX 输出能确定加固风格，却不足以判断业务 DEX 在哪里。
2. 从 OAT 目录抽出 VDEX 后仍可能只得到壳，文件大小没有判定价值。
3. 可 root 的 userdebug 环境、目标页面的真实执行和 `/proc/<pid>/mem` 才构成这次恢复业务 DEX 的条件。
4. 扫描 DEX magic 后必须继续校验头部边界并去重，粗暴转储全部映射会制造数百 MB 噪声。
5. 恢复出的业务状态机解释了原版怎样用左右两个 View 分离时间窗口拖动和时间块选择。

## 推荐结构

1. 结果和研究边界
2. 静态路线留下的壳证据
3. VDEX 路线为何失败
4. userdebug 环境与运行时内存
5. DEX 扫描、校验和结果
6. 业务代码怎样纠正黑盒误判
7. 可复用的排障清单与局限
