# 审校意见：360 加固 APK 的识别、运行时 DEX 恢复与常见坑

## 总体评价

文章方向与选题卡一致，样本结论和适用边界大体写清楚了，也没有展开产品复刻、UI 交互或具体业务逻辑。当前主要问题集中在可复现性和 DEX 统计口径：照文中的分块建议执行可能漏掉完整 DEX，表格中的“方法数”也容易被读者理解成方法定义数。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[“从 maps 找范围，再从 mem 取内容”第 4 条]** “相邻块保留至少 `0x70` 字节重叠，避免 DEX 头跨块”只能保证跨块的头部可能被发现，不能保证后续 `file_size` 指向的完整 DEX 位于同一个快照文件中。紧接着的 Python 示例明确不做跨文件拼接，因此一个头落在块尾、主体落在后续块中的正常 DEX 会因 `end > len(blob)` 被直接丢弃。→ 建议：把方案改为流式扫描原始映射；发现合法头后按 `file_size` 从该虚拟地址继续读取完整候选。若坚持分块落盘，则必须保存映射基址并实现相邻块拼接，不能把 `0x70` 重叠写成完整解决方案。

2. **[“十一份候选怎样分类”表格及全文“方法数”表述]** 表中的 `methods` 来自 `method_ids_size`，它统计的是该 DEX 的方法标识符，包括本文件定义的方法以及对外部方法的引用，不等于“类中实际定义了多少方法”。“4 个类和 190 个方法”等表述会让读者误以为这是方法定义数。→ 建议：把表头统一改成 `method_ids` 或“方法 ID 数”，正文也使用同一口径；如果需要方法定义数，应遍历 `class_data_item` 中的 direct/virtual methods 单独统计。

3. **[“从 maps 找范围，再从 mem 取内容”整节]** 标题和操作清单承诺“从 `/proc/<pid>/mem` 分块读取”，但正文只展示了读取 `maps` 的命令，关键步骤只写成文字；唯一的 Python 代码要求读者预先已有 `memory-dumps/*.bin`。读者无法据此复现实验，也无法知道地址、长度、读取失败和虚拟地址基准如何处理，不符合“代码必须能跑”的标准。→ 建议：补一段最小可运行的采集脚本或明确可验证的工具命令，至少解析 `start-end`、只处理 `r` 映射、从 `/proc/$PID/mem` 定位读取、记录映射起始地址并处理短读；若出于安全边界不公开采集代码，就把文章定位改成“结果与判定方法”，不要称其为可复用操作清单。

### 🟡 建议修改（影响表述质量）

1. **[“十一份候选怎样分类”工具建议]** “`apkanalyzer dex packages`”缺少必需输入，且该命令通常面向 APK 文件，直接拿单个内存导出的 `.dex` 使用容易失败。→ 建议：给出经过验证的完整命令及工具版本；若没有实测 raw DEX 输入，改举 `dexdump`、JADX 单文件输出或文中的 descriptor 解析脚本。

2. **[结尾“处理同类 `StubApp` 时，可以直接复用”]** `StubApp` 是过宽的入口类名，不能单独代表与本样本相同的壳家族、加载路径或内存形态。“直接复用”略微扩大了单一样本经验。→ 建议：改为“遇到同时符合 `StubApp`、`libjiagu_*` 等特征、且业务代码以标准 DEX 进入 ART 的样本时，可把这套顺序作为排查起点”，并保留重新验证 ABI、加载时机和头部状态的要求。

### 🟢 可选优化（锦上添花）

1. **[全文结构]** 文中涉及 APK、壳 so、ART、映射、内存快照和多个 DEX 候选，组件超过两个。→ 建议：增加一张小流程图，标明“APK 静态信号 → 运行触发 → `/proc/<pid>/maps` 定位 → `/proc/<pid>/mem` 读取 → 头部校验与哈希去重 → descriptor 分类 → JADX/Smali 核验”，能减少读者在 maps、snapshot 与候选 DEX 三者之间来回对照。

## 亮点

“符合 360 加固家族特征”与“精确识别壳版本”区分得清楚；对 VDEX、大文件体积和合法 DEX 头的误判提醒也有实际价值。文章还明确列出方法级解密、虚拟化、CompactDex 和 native 化的边界，并用目标包 `class_defs` 与 JADX Java 文件数解释统计口径差异，这些内容值得保留。
