# 审校意见：Context rot 不是一种病

## 总体评价

文章的主线清楚，能把读者熟悉的“agent 越改越乱”拆成两个可诊断的问题，整体没有偏离选题卡。但现在最大风险不是表达，而是证据链：几处关键论文、数字和产品/报告结论没有给足来源或限定条件，容易把“旁证”和“coding agent 场景的结论”混在一起。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **“`/compact` 治的是长度，不一定治污染”一节，论文段落**：`Contextual Drag` 和 `Latent Phase-Shift Rollback` 直接承担了“错误 context 会拖拽后续推理、自我纠错不可靠”的关键论据，但正文没有给原始链接、作者/年份，也没有说明适用范围。尤其是 LPSR 的 24.2 个百分点来自特定实验设置，不等于 coding agent 重开上下文一定优于 prompt 自纠错。→ 建议：给两篇论文补原文链接，并在句子里补限定，例如“在其数学推理/推理任务设置中”“只能作为机制旁证，不能直接外推到 coding agent”。

2. **“太脏：错误前提进了 context”一节，Gemini Plays Pokemon 段落**：`这个词不是视频作者凭空造的` 里的“视频作者”在正文中没有交代，像是残留的素材来源；同时对 Gemini 2.5 技术报告的转述需要更精确到报告章节或页码。现在读者只能看到 PDF 链接，无法判断“错误信息污染、追求不可能目标、很久才能解开”是不是原文意思。→ 建议：删掉“视频作者”这句，改成“Google DeepMind 在 Gemini 2.5 技术报告的 Gemini Plays Pokemon 讨论中使用了 context poisoning 这个说法”，并补页码/章节或脚注。

3. **“太长”一节，Anthropic 84% / 39% 数据后的结论**：`足以说明：治理“太长”，工程手段确实有效` 表述过宽。Anthropic 原文数据来自内部 agentic search / 100-turn web search evaluation，不是 coding agent 修 bug 场景；“工程手段确实有效”也容易被读成通用结论。→ 建议：改成“至少说明，在 Anthropic 的长轮次搜索评测里，context editing / memory 能显著改善 token 消耗和任务表现；放到 coding 场景还需要单独验证”。

4. **“Sub-agent 的价值可能在隔离失败路径”一节，90.2% 数据**：`Anthropic 在一篇工程文章里说...高 90.2%` 是精确数字，但没有链接；并且这个数字来自 internal research eval，Anthropic 同文还明确说 coding 任务通常不像 research 那样适合大规模并行。正文有提到限制，但数字本身仍缺来源。→ 建议：给 Anthropic 工程文补链接，并把“比单 agent Claude Opus 4 高 90.2%”改成“在其内部 research eval 中高 90.2%”，避免读者误解为 multi-agent 对 coding agent 普遍提升。

5. **“先问：太长了，还是太脏了”与结尾，经验判断写成了普遍规律**：`症状通常是“漏”`、`症状通常是“执着”`、`继续勾兑通常只会让错误前提更难清理` 这些判断是文章最有用的部分，但目前缺少来源或作者经验边界。它们可以成立为实践经验，不能像已验证诊断规则一样写死。→ 建议：加一层限定：“我的使用经验里，可以先用这个启发式判断”“它不是严格分类器”，或者补一个真实 debug 小案例支撑。

### 🟡 建议修改（影响表述质量）

1. **开头 taxonomy 定义处**：`distraction：长度问题。context 太长，信号被稀释。` 这个命名可能和 Chroma 报告里的 `distractors` 概念发生混淆；Chroma 的 distractor 是“相关但错误/不回答问题的信息”，不只是长度本身。→ 建议：明确 `distraction` 是本文自定义的操作性标签，或者换成更不冲突的名字，比如 `overload` / `dilution`。

2. **“这两个问题的解法完全不同”**：`完全不同` 过于绝对。实际处理上二者有交集，例如 sub-agent、重新读取事实、最小事实集整理都同时服务于降噪和隔离污染。→ 建议：改成“优先级不同”或“第一反应应该不同”：太长先压缩，太脏先清理/隔离。

3. **“太脏”一节，5 步 poisoning 形成过程**：这段很直观，但现在是一个抽象流程，没有真实案例或最小复现，读者可能会觉得是合理想象而不是经验总结。→ 建议：增加一个 4-6 句的真实/匿名案例，至少说清楚“错误假设是什么、哪条测试或日志否定了它、agent 如何继续维护它”。

4. **“/compact”一节，缓存例子**：缓存例子承担了“摘要器会保留错误假设”的说明，但它仍是假设式描述，缺少“摘要器为什么会保留它”的具体机制或观察。→ 建议：补一段更具体的旧会话摘要片段示例，比如错误摘要如何把“缓存可能是根因”写成“当前排查集中在缓存层”，让风险更可见。

5. **结尾两段**：`正经药`、`继续勾兑` 有作者味，但最后的落点略像口号，缺少一个更硬的 takeaway。→ 建议：把结尾压成一条可执行规则，例如“下一轮 prompt 只带现象、约束、已验证事实；不带未验证根因、失败 diff、基于失败 diff 的解释”。

### 🟢 可选优化（锦上添花）

1. **标题**：现在的标题有观点，但“不是一种病”略抽象。可以考虑更直接面向读者痛点，例如“Agent 越改越烂，不一定是 context 太长”。

2. **表格诊断项**：`需要探索多个方向 | 两者都可能 | 用 sub-agent 隔离探索过程，只回传结论` 很有用，可以再加一列“不要带什么”，强化本文差异点。

3. **来源呈现**：文章引用来源较多，建议统一把论文和官方文章都做成 Markdown 链接，避免有的链接内嵌、有的只写名字，降低事实核查成本。

## 亮点

“太长 vs 太脏”的框架值得保留，尤其是“只带真实现象、明确约束、已验证事实进新会话”这一组操作建议，能直接转化成读者的 agent 使用习惯。文章的语气整体不像企业稿，示例 prompt 也具体，后续主要是把证据边界补牢。
