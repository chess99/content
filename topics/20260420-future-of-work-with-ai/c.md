# AI 时代研发大闭环：从“写代码”到“建流程”的范式转移

在 2026 年的今天，当我们环顾整个软件工程领域，会发现所有走在前沿的团队（无论是大厂还是先锋创业者）都在做同一件事：**卷研发流程的大闭环**。

从淘宝闪购的“全栈实战”到网易的“智能化软件工厂”，从百度的“飞轮闭环”到我们自己仓库里的 `aiworkflow` 试点，无一不在试图将 PRD 解析、架构设计、编码、测试验收、上线发布这 7 个阶段连成一线。

但在这个喧嚣的“大闭环”浪潮中，我们必须看清一个本质的范式转移：**AI 时代，我们需要的不再是写代码的人，而是建流程的人。** 写代码只是执行层的一种体力活，所有执行层的事情，最终都可以、也必将由 AI 来干。未来的高级工程师，其核心资产不是写出了多么精妙的算法，而是能否设计出一条让 AI 稳定、高效运作的“数字流水线”。

基于各大厂的真实落地经验和我们自身业务的痛点，我们需要重新定义未来的工作方式。

---

## 一、 为什么“大闭环”这么难？大厂探索的启示与局限

把研发各个环节串起来听上去很美，但实际上各家在落地时都面临着实质性的困难。

**1. 淘宝闪购的困局：闭环的尽头是极度复杂的工程挑战**
淘宝闪购把 AI 编码率从 9% 提升到了 89.2%，并且提出了“Rules（宪法） + Spec（法规） + Skills（执法机构）”的三位一体架构。他们看到了大闭环的方向（从需求到上线），但实际上目前仍停留在**单节点的极致优化（单工程项目级的代码生成）**。当上下游节点真正打通时，如何保证跨节点的上下文不丢失？如何防止上游的微小幻觉在下游引发雪崩？这些实质性的困难，单纯依靠约束提示词是解决不了的。

**2. 蚂蚁的破局洞见：不再试图让人舒服，而是让 AI 舒服**
蚂蚁的 Vibe Coding（Muse 平台）之所以能在内部月活破万，核心在于他们跳出了“程序员中心主义”。他们得出了一系列振聋发聩的“暴论”，而这些正是建立流程大闭环的前提：
*   **基建必须天生 AI 友好**：GUI 不再重要，一切能力必须 CLI 化。
*   **文档是写给 AI 看的**：放弃供人阅读的漂亮排版，全面拥抱 `llms.txt`。
*   **文件即记忆，一切由 Git 管理**：AI 跨 Agent 沟通用自然语言损耗极大，必须通过持久化的文件和 Git 树来进行状态流转。
执行层的事情，核心已经变成**如何给 AI 提供便利**，而不是给人提供便利。

**3. PayPal 的工程解法：用“对抗测试”定义流程的边界**
如何让流程真正可控？PayPal 给出了教科书般的答案。他们没有把精力全花在“怎么让 Agent 写对代码”上，而是构建了一个包含 150+ 种噪声类型的**测试数据工厂（Noise Catalog）**。
他们故意在代码里加入拼音变量、错乱的架构、互相冲突的逻辑，以此来“攻击”Agent。只有在 EERO 循环（执行→评估→反思→优化）和海量噪声测试中活下来的 Skill，才配进入生产流程。**用一整套严密的最终测试来清楚描述预期，才是流程可控的唯一手段。**

## 二、 审视我们的现状：手工作坊与自动织布机的断层

反观我们自身的业务场景，存在着明显的断层，这正是我们接下来要发力的方向。

看看我们调研的两个仓库：
*   **`<internal-business-repo>`**：这是一个典型的、沉重的业务线开发仓库。里面有 56 个卡片模板，大量的业务逻辑和定制化的 UI。目前，**他们还在手动开发**。每次迭代，开发者都在人工阅读文档、人肉编写 Less 和 TSX、人工将结果塞入 `.check-work` 目录。因为是人工在做，所以**没有任何 AI 可以消费的“经验”被沉淀下来**。
*   **`aiworkflow`**：这是一个极具前瞻性的架构。它定义了 7 个阶段的 FSM 状态机，定义了 `base_agent`，定义了审批流。但它目前**非常早期，基本只是一些 Demo 和 Mock 数据**。

**未来的方向非常明确：用 `aiworkflow` 这个“自动织布机”，去吃掉 `<internal-business-repo>` 里的所有“手工活”。** 

把 `<internal-business-domain>` 里的模板创建、语法检查、动态测试、埋点验证，全部抽离成 `aiworkflow` 里的独立 Skill（如已经初见端倪的 `ec-case-code-checker`）。这就要求我们，必须停止把精力放在具体的业务代码实现上，而是转过头来，去搭建那条流水线。

## 三、 深度思考：流程是如何建立并运作的？

“建流程”听起来很宏大，但它到底意味着什么？结合我之前在处理 QCon 语音转写逐字稿时的经验，以及我对“Skill 整洁架构”的思考，流程的建立与运行分为两个截然不同的阶段。

### 阶段一：初期的“泥泞期”（人为主导的 Harness 建设）
正如处理那 9 篇大会逐字稿一样，一开始，AI 的理解和我的意图是完全错位的。它想写脚本，我想要语义重写；它把“歌儿”推断成不存在的东西，它被 OCR 的错误参数误导。

**这个阶段，人的参与是不可替代的。** 
你需要亲手跑通流程，去踩坑。你必须：
1.  **明确输入输出协议**：像《架构整洁之道》里说的那样，把 Skill 拆分。定义好“拉取测试用例”（Base Skill）和“执行代码检查”（业务 Skill）之间的 JSON 契约。
2.  **提供高质量的信息环境**：给 AI 提供 `llms.txt`、提供官方演讲摘要，**给 AI 更好的信息，永远比给 AI 更好的 Prompt 更有效。**
3.  **制定 SOP 与注入噪声**：像 PayPal 那样，把踩过的坑（比如 OCR 的 `--psm 6` 参数）写进 Skill 的上下文中。故意设计边界情况，看 AI 是否会崩溃。
4.  **建立独立评估者（Evaluator）**：生成与验证必须分离。主干 Agent 写代码，必须有另一个上下文干净的 Agent 来挑刺。

### 阶段二：建好后的“飞轮期”（AI 自动执行，人退居观测）
当那 9 篇文章的 SOP 固化后，最后两篇从入库到输出排版好的文章，全自动只花了 **8 分钟**。我的介入只剩下提供原始素材和偶尔看一眼不确定的 `[?]` 标记。

未来的研发流程也将是如此。一旦 `aiworkflow` 和 `<internal-business-domain>` 之间的通道彻底打通：
1.  **产品经理**在系统里提交一段自然语言需求或一张交互稿。
2.  **PRD Agent** 自动将其转化为 EARS 标准的结构化需求文档，人只需要点击“Approve”。
3.  **Tech Plan Agent** 调取当前仓库的 `AGENTS.md` 和架构文档，生成技术方案，人只需看一眼接口设计。
4.  **Coding Agent** 和 **QA Agent** 开始在底层疯狂搏杀：Coding Agent 写出代码，QA Agent 按照前置提取的测试用例进行校验，失败则打回重写（在这个微循环中，AI 自己在 Review 自己，数百次的交互在几分钟内完成）。
5.  **最终**，流程停止，抛出一份通过了所有自动化校验、埋点测试、语法检查的 Diff 供最终的 Human Review。

在这个阶段，人类工程师变成了**流程监控员**和**系统调优师**。我们只需要盯着通过率、Token 消耗率、Bug 遗漏率这些“指标”，如果发现异常，我们就去修改对应 Skill 的 SOP 或完善知识库文件。

## 四、 未来工作方式的蓝图与推演

面对正在加速到来的 AI 软件工厂，我们团队以及个人的工作范式必须发生深刻的转变。未来我们要往上下游卷，把庞大的研发流程拆成一个个独立的、基于状态机的微流程。

**1. 组织架构即系统架构（逆康威定律的应用）**
不要再按照“前端/后端/测试”来划分团队。在 `aiworkflow` 的建设中，我们需要设计的是 **Agent 的团队架构**。
我们需要定义：谁是 Planner（规划者），谁是 Executor（执行者），谁是 Reviewer（审查者）。我们分配给 Agent 的职权边界，最终就会变成我们整个研发系统的软件架构。Skill 就是他们之间的沟通协议，文件目录就是他们的会议室。

**2. 交付物的彻底改变：从“交付代码”到“交付验证闭环”**
正如 PayPal 分享中所说，未来我们交付给用户的，不再仅仅是一堆功能代码，而是 **“Skills 集合 + 一整套严密的测试集”**。
只要测试集（Test Suite）足够健壮、能覆盖 100% 的边界和噪声，那么中间生成代码的过程哪怕是一个完全的黑盒，我们也能安然入睡。**“评测即开发”**，写好 Benchmark 和验收规则，将占据我们工作的绝大部分时间。

**3. 基础设施的全面改造：面向 Agent 编程**
现有的各种系统（Jira、GitLab、设计平台、测试平台）对 AI 都极其不友好。我们必须：
*   把所有高频的研发操作封装成 **CLI 工具**。
*   把深埋在文档系统里的业务经验，提取转化为 **结构化的 `llms.txt` 和 Skill SOP**。
*   摒弃复杂的 API 鉴权，为内部系统提供一套专门针对 Agent 身份的授权体系。

**4. 持续进化的 Compound 记忆工程**
不能让大模型每次都像初学者一样重读整个代码库。我们需要借鉴网易和 MemTensor 的经验，在 `aiworkflow` 中引入图谱化的长短期记忆。每次 `<internal-business-repo>` 里的需求迭代成功，或者踩了一个坑，必须由总结 Agent 提取出“血泪教训”，固化为该工程的长期记忆（比如更新项目级的 `CLAUDE.md`）。让系统本身成为一个会“自我进化”的生命体。

## 结语：让代码自己写自己

Dijkstra 曾说用自然语言编程是愚蠢的，因为失去了形式化符号的数学约束。这句话在 AI 时代依然成立。但解法变了：我们不需要让人去写约束，我们需要**用一套工程化的机器流水线去约束 AI**。

在这个大闭环里：
*   **输入端**用 EARS 规范和标准 DSL 锁死歧义。
*   **执行端**用 CLI、渐进式知识加载（Skill）和多 Agent 协同来保证专注。
*   **输出端**用极其变态的噪声测试和独立 Evaluator 来兜底质量。

**未来的工程师，就是这条流水线的总设计师。** 
当别人还在沉迷于用 Cursor 快感满满地敲出一个个页面时，我们应该抽身出来，去建设 `aiworkflow` 这样的枢纽。把那几百个前端卡片模板的生产逻辑抽丝剥茧，变成固化的流程，让机器去管理机器。

因为在 AI 时代，代码只是副产品；**跑通、固化并能持续自我迭代的“流程”，才是企业与个人最核心的壁垒。**
