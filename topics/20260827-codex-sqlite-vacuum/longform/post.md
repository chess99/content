# Codex 吃了我 40GB C 盘？用 Claude 一条 Prompt 找回 26GB

**导语：** 用了几个月 Codex 后，C 盘突然红了。SpaceSniffer 一扫，`.codex` 目录占了 40GB，其中 `logs_2.sqlite` 一个文件就 27GB。更离谱的是，里面 97% 都是"空页"——有效数据只有 742MB。本文记录从发现问题到用 Claude Code 一条 prompt 安全回收 26GB 的全过程，并深入解释 SQLite 为什么会这样、怎么避免。

---

## 背景

我一直用 Codex（Anthropic 的本地 AI 编程助手）做日常开发。几个月下来，C 盘开始频繁告警。用 SpaceSniffer 扫描后，发现凶手是：

```
C:\Users\zcs\.codex\   → 40GB
  └── logs_2.sqlite    → 27GB  ← 罪魁祸首
```

在此之前，我对 SQLite 文件膨胀几乎没有概念——不就是个日志数据库吗，能大到哪去？

## 发现过程

第一步：用 SpaceSniffer 找到大文件。第二步：用 SQLite 工具检查内部状态：

```sql
PRAGMA quick_check;              -- ok
SELECT COUNT(*) FROM logs;       -- 144,249 条
PRAGMA freelist_count;           -- 约 97% 的页是空闲的
```

14 万条日志，正常人不会觉得"太多"。但 27GB / 14 万 ≈ 每条日志近 200KB——这显然不是真实数据量。真正的原因是 **SQLite 的删除操作不释放磁盘空间**，Codex 反复写入→清理旧日志→写入→清理，空闲页越积越多，文件像吹气球一样膨胀。

## 问题原因（一句话版）

SQLite 默认模式下，DELETE 只是把数据页标记为"可复用"，并不归还给操作系统。Codex 高频滚动清理日志，每次清理都产生大量空闲页，文件永远只增不减。

## 处理方式（一句话版）

不能用普通的 `VACUUM`（它会在 C 盘原地重建，需要额外 27GB 临时空间），改用 `VACUUM INTO` 在 D 盘生成压缩副本，验证后替换。

## 深入原理：SQLite 为什么白白占用这么多空间？

### 1. SQLite 的存储模型：页（Page）

SQLite 把数据库文件划分为固定大小的"页"，默认每页 4KB。所有数据——表记录、索引、元信息——都存储在这些页中。数据库文件的大小 = 页数 × 页大小。

```
┌──────────────────────────────────────────────────────────────┐
│  SQLite 数据库文件（逻辑视图）                                  │
│                                                               │
│  [Page 0]  [Page 1]  [Page 2]  ...  [Page N]                 │
│   ↑         ↑         ↑               ↑                       │
│   文件头    数据页    数据页          文件末尾（高水位线）        │
│                                                               │
│  文件大小 = N × 4KB。即使中间页全是空的，N 也不会变小。           │
└──────────────────────────────────────────────────────────────┘
```

### 2. Freelist：删除不是真的删除

当你执行 DELETE 或 UPDATE（本质是 DELETE + INSERT）时，SQLite 不会把对应的页归还给文件系统。它只是把这些页的"使用中"标记去掉，然后链入一个叫 **freelist**（空闲页链表）的内部结构中。

```
删除前：每页都标记为"使用中"
[Page 1: used] [Page 2: used] [Page 3: used] [Page 4: used]

DELETE 后：被删数据的页进入 freelist，文件大小不变
[Page 1: used] [Page 2: FREE] → [Page 3: FREE] → [Page 4: used]
               ↑ freelist 链表头              ↑ freelist 尾

文件还是 4 页大，但只有 2 页有实际数据。
```

后续 INSERT 新数据时，SQLite 会优先从 freelist 中取页来复用，而不是在文件末尾追加新页。**这很聪明，但有一个致命后果：文件大小永远不会自动缩小。**

### 3. "高水位线"：为什么文件只增不减

SQLite 记录一个"高水位线"——文件曾被使用过的最大页号。这个值只会增长，不会回退。

```
第 1 天：写入 10 万条日志 → 200MB，高水位线 = 页 50,000
第 2 天：清理旧日志 DELETE → 文件还是 200MB，空闲页 97%
第 3 天：写入新日志 → 复用 freelist 页，可能小幅增长到 250MB
第 4 天：清理 → 还是 250MB，空闲页 95%
...
第 N 天：经过数百次写入/清理循环，文件膨胀到 27GB，高水位线 = 页 7,000,000
```

**即使某一时刻只有 1% 的页在使用，文件的"高水位线"也永远不会下降。** 这是 SQLite 有意为之的设计选择——磁盘空间便宜，数据安全更重要，宁可留着空间也不冒险收缩。

### 4. Codex 日志场景的具体放大效应

Codex 的日志模式是典型的"空间膨胀加速器"：

```
高频写入（每次对话产生大量日志）
    +
高频清理（定期清理旧日志，DELETE 操作）
    +
SQLite 默认 freelist 策略（不归还磁盘）
    =
文件持续膨胀，直到手动干预
```

还有一个被忽视的副作用：**即使 97% 的页是空闲的，操作系统在内存映射文件时仍然需要处理整个 27GB 的文件**。每次全表扫描或索引遍历，都要跨越大量空洞页，拖慢查询性能。

### 5. VACUUM 是怎么工作的

`VACUUM` 的原理很简单：**创建一个全新的数据库文件，只复制"使用中"的页，丢弃所有 freelist。**

```
VACUUM INTO 的执行过程：

  原库（27GB）                    新库（742MB）
  ┌──────────────┐                ┌──────────────┐
  │ Page 1: used │ ──复制──→       │ Page 1: used │
  │ Page 2: FREE │  (跳过)         │ Page 2: used │
  │ Page 3: FREE │  (跳过)         │ Page 3: used │
  │ Page 4: used │ ──复制──→       │ Page 4: used │
  │ ...          │                │ ...          │
  │ 7,000,000 页 │                 │ 185,000 页   │
  └──────────────┘                └──────────────┘
     97% 空闲                          0% 空闲
```

`VACUUM INTO` 相比 `VACUUM` 的关键优势：**原库只读，不产生临时文件，新库直接写到指定路径。** 这让你可以在 C 盘空间不足的情况下，把压缩副本写到 D 盘，验证后再替换。

### 6. 三种预防方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **定期 VACUUM** | 手动重建数据库，回收所有空闲页 | 彻底回收，操作简单 | 需要停机，大库耗时长 |
| **`PRAGMA auto_vacuum=FULL`** | 删除时自动归还磁盘空间 | 文件始终保持最小 | 写入性能下降，需建表前设置 |
| **`PRAGMA auto_vacuum=INCREMENTAL`** | 手动调用 `incremental_vacuum` 逐步回收 | 灵活控制回收时机 | 仍需手动触发，不能完全自动化 |

对于 Codex 这类应用，**最实际的做法是定期 VACUUM**。你不可能要求 Codex 改变数据库创建方式（`auto_vacuum` 必须在建表前设置），但你可以每隔几周（或 C 盘告警时）执行一次压缩。

### 7. 为什么选 VACUUM INTO 而不是原地 VACUUM

```
C 盘原地 VACUUM：
  原库 27GB + 临时文件 ~27GB = 需要 ~54GB 可用空间
  但 C 盘可能只剩不到 10GB → 直接失败

VACUUM INTO 'D:\...'：
  原库在 C 盘，只读不写
  新库在 D 盘，需要 ~742MB 空间
  不需要 C 盘任何额外空间
```

这就是为什么即使你 C 盘有空间，也建议用 `VACUUM INTO` 到另一个盘——它不依赖原盘剩余空间，且原库全程只读，安全性更高。

```
┌─────────────────────────────────────────────────────────────┐
│  SQLite 的默认行为：DELETE 不释放磁盘 → 文件只增不减           │
│                                                              │
│  Codex 场景：高频写入 + 高频清理 → 97% 空闲页 → 27GB 文件     │
│                                                              │
│  解决方案：VACUUM INTO 到其他盘 → 742MB 纯数据副本 → 替换     │
│                                                              │
│  预防：定期 VACUUM，别无他法                                  │
│                                                              │
│  关键教训：SQLite 的文件大小 ≠ 数据量，它可能比你想象的大 36 倍  │
└─────────────────────────────────────────────────────────────┘
```
