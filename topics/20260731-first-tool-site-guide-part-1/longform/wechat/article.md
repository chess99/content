我用 AI 大约一小时做出了 MarkGleam 的可用首版，接下来两三天才开始回答一个更难的问题：它值不值得继续做？

第一次做工具站，最容易把时间用在 Logo、域名、登录、支付和一长串“以后肯定需要”的功能上。真正要尽早确认的只有四件事：问题是否真实，用户能不能完成任务，你能不能找到他们，他们用完还想解决什么。

这篇给出一条可以照着执行的上站路线：先扫一遍市场，做出最小闭环，尽快放到公网，找真实用户交作业，再用反馈和搜索意图决定下一步。账号、支付和授权先留到下篇，等它们真的被做完再谈。

## 一个小时能做首版，做不成完整产品

MarkGleam 的起点很简单：我有一段 Markdown 想分享给朋友，本地截图不方便生成长图；网上的转换工具有些不好看，有些带水印，有些需要订阅。

我把需求交给 AI，大约一小时后，粘贴 Markdown、实时预览、导出图片的主流程已经能用了。纯前端页面直接放到 GitHub Pages，不买独立域名也能使用默认的 `github.io` 地址。

如果故事停在这里，很容易得出一个错觉：工具站已经做完了。

后面两三天的任务列表却越来越长：PDF 导出黑图、移动端滚动、Safari 兼容、语言切换、域名迁移、开源许可、搜索页面、统计事件……首版只是证明代码能跑，产品要证明陌生人也能把事情做完。

所以，有了点子之后别立刻开十个开发任务。先给自己一个小时，回答下面的问题。

## 先写问题卡，再看市场

问题卡不用做成商业计划书，一页纸就够：

1. **谁在什么场景下遇到问题？** 不写“内容创作者需要效率工具”，写“经常把 Markdown 报告发给非技术朋友的人，需要一张手机上能直接看的长图”。
2. **他现在怎么解决？** 截图、复制到 Word、找在线工具、手工排版，或者干脆不做。
3. **现有办法哪里难受？** 费时间、结果难看、带水印、隐私不放心，还是价格超过了使用频率？
4. **做完以后，结果怎么被带走？** 下载、复制、分享链接、导入别的软件。没有“带走”，工具闭环就缺了一块。

接着做一轮限时市场扫描。我的建议是 30—60 分钟，不要查成毕业论文。

- 搜核心任务词，看前十个结果在解决什么；
- 看三到五个竞品的定价、限制和差评；
- 去小红书、知乎、Reddit、GitHub Issues 或垂直群里搜用户原话；
- 记下用户使用的词，不要只记产品经理喜欢的词。

可以用下面五项给机会做个粗判，每项记 0—2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 问题强度 | 可有可无 | 有点麻烦 | 会阻断任务 |
| 出现频率 | 很偶发 | 每月几次 | 每周或更高 |
| 用户可触达 | 不知道去哪找 | 能找到社区 | 手上就有目标用户 |
| 现有缺口 | 已经很好解决 | 有局部不满 | 普遍要忍受明显代价 |
| 首版可行性 | 依赖重服务或资源 | 能做原型 | 几小时能闭环 |

这张表不是科学模型，也不需要迷信总分。它的用处是暴露最弱的一项。比如搜索量很好看，但你完全找不到第一批用户；或者抱怨很多，实际解决方案只值一次手工操作。看到这种断点，就先缩小问题。

## MVP 按任务闭环切，不按功能数量切

很多人理解的 MVP 是“少做几个功能”。更好用的切法是保住一条完整路径：

```text
输入 → 处理 → 检查结果 → 带走结果
```

以 Markdown 转图片为例：

- 输入：粘贴或输入 Markdown；
- 处理：正确渲染标题、列表、代码块和图片；
- 检查：能看到最终排版和尺寸；
- 带走：稳定导出 PNG，文件能正常打开。

主题商店、团队空间、云端历史、会员等级都可以没有。导出的图片只有 72B，或者 PDF 打开一片黑，再漂亮的编辑器也没有完成任务。

此时还应单独写一份“不做清单”。第一次上线通常可以先不做：

- 账号和登录；
- 支付与套餐；
- 自定义域名；
- 后台管理系统；
- 十几种相似模板；
- 为每个关键词复制一张页面。

纯前端工具很适合用 GitHub Pages、Cloudflare Pages 或 Vercel 快速发布。MarkGleam 首版用了 GitHub Pages，自定义域名是后来才加的；没有独立域名并不妨碍把 `github.io` 链接发给第一批用户。

上线前留一点最小观测能力就够了：

- 页面是否打开；
- 用户是否开始输入；
- 是否成功看到结果；
- 是否成功导出；
- 失败发生在哪个步骤。

如果产品处理的是文档、图片或代码，统计事件不要上传用户正文。事件参数只记步骤、结果和必要环境信息；文件名、正文、URL 查询参数和原始错误内容先脱敏，能聚合就不留明细。

## 第一个真实用户，比第一百个访客重要

新工具上线后，先别盯着 PV 刷新。你需要找几个人完成一次真实任务。

发布内容也别只写“我做了一个网站，欢迎体验”。把问题、结果和适用对象说清楚：

> 如果你经常需要把 Markdown 发给不使用 Markdown 的人，可以试试这个转换工具。请拿一份真实文件完成导出；如果失败，把操作步骤、浏览器和脱敏后的样本发给我。

图片版上线后，我又加了仍在试验的 PDF 导出。一位用户拿真实文件测试，并反馈 PDF 导出为黑图。更关键的是，对方愿意提供原始文件。这个样本让问题从“某个用户说不能用”变成了可复现的故障，后来一路查到隐藏预览节点、透明画布和离屏截图，修复后又补了 Chromium、Firefox、WebKit 的回归测试。

收反馈时尽量拿到六样东西：

1. 用户原本想完成什么；
2. 输入样本，必要时脱敏；
3. 完整操作步骤；
4. 实际结果；
5. 期望结果；
6. 浏览器、设备或运行环境。

一个失败样本不能证明市场很大，却能暴露当前任务闭环在哪条路径上断了。对早期工具来说，这往往比“挺好用的”更值钱。

## 用搜索意图决定做什么，不用关键词堆页面

用户开始使用之后，再回头做关键词研究，此时已有产品边界和用户任务作为参照。

MarkGleam 最初围绕“Markdown 转图片”开发。我在 2026-07-30 查询 Semrush Keyword Overview 的美国和全球数据库时，`markdown to pdf` 的估算量分别是 8.1K 和 72K，`markdown to image` 分别是 90 和 270。关键词工具给出的是第三方估算，不等于网站能得到的流量，更不等于付费需求。它提出了一个值得验证的问题：用户真正想带走的结果，会不会主要是 PDF？

扩词可以按这张表整理：

| 关键词簇 | 用户任务 | 产品是否真的不同 | 处理方式 |
|---|---|---|---|
| markdown to image / png / md to image | 把 Markdown 变成图片 | 基本相同 | 同一页承接 |
| markdown to pdf | 得到分页、可打印的文档 | 输出与分页逻辑不同 | 独立能力或页面 |
| mermaid to image | 把图表代码变成图片 | 输入和预览不同 | 值得单独承接 |
| 小红书 Markdown 转图 | 为平台准备尺寸 | 主要是预设差异 | 先做真实预设 |
| markdown API | 自动化批量转换 | 当前没有 API | 不建空页面 |

页面数量不是 SEO 进度。只有输入模型、默认状态、编辑流程或输出结果明显不同，才值得建立独立 URL。同义词、格式名和平台名可以自然写进同一页；为近似查询批量复制页面，既增加维护成本，也可能落入 Google 对 doorway abuse 的判断。

上线后再用 Search Console 的 Performance report 看真实查询：用户搜了什么、落到哪一页、有没有展示却没人点。新站几天没有数据很正常，别用三五次展示宣布方向成功或失败。

## 变现先选价值，再选支付工具

变现讨论很容易提前变成“接 Stripe 还是接支付宝”。更早该回答的是：用户为什么愿意付钱？

| 模式 | 更适合什么情况 |
|---|---|
| 一次性买断 | 使用不算高频，但一次能省下明确时间；本地功能为主，持续成本低 |
| 订阅 | 持续提供同步、存储、团队协作、云渲染、API 或内容更新 |
| 按量计费 | 每次调用都会产生可计算的模型、带宽或渲染成本 |
| 广告 | 已有较大内容流量，广告不会破坏核心操作和隐私承诺 |
| 免费 | 用于验证、传播、开源生态，或为另一项服务获客 |

MarkGleam 目前考虑的是：免费 Web 版负责使用和传播，未来可能用买断版提供无署名、自定义品牌和桌面批量；只有同步、团队、云渲染或 API 出现真实需求，才考虑订阅。这只是当前假设，还没有经过付费验证。

用户主动询问去署名、自定义品牌、批量处理、团队模板或 API，比凭空设计套餐更值得记录，但它们仍然只是候选付费信号。下一步还要通过价格访谈、带明确价格的意向登记或小额预售确认支付意愿，再承担账号、支付、许可证、退款和税务成本。

## 一份可以直接照做的七天清单

- **第 1 天**：写问题卡，搜十个结果、三个竞品和十条用户原话；
- **第 2 天**：只做一条“输入—处理—检查—带走”闭环；
- **第 3 天**：补最危险的边界情况，接最少事件，上线默认域名；
- **第 4 天**：把链接发给能完成真实任务的人，不追求泛流量；
- **第 5 天**：争取拿到一个成功样本和一个失败样本；暂时没有就继续定向触达和观察；
- **第 6 天**：整理关键词簇，把同义词、独立意图和暂不做的能力分开；
- **第 7 天**：决定继续、缩小或暂停，并写下下一轮只验证什么。

七天后先检查三项产出：一条真的能跑通的任务路径、至少一个真实用户样本、一个有证据的下一步。暂时没有赚到钱很正常；样本还没出现，就继续触达，不要为了赶清单制造结论。

账号和支付什么时候加？等你能说清楚付费对象、付费价值和交付边界再加。下篇我会等 MarkGleam 真正做完登录、支付与授权后，再把技术选择、踩坑和账算明白。
