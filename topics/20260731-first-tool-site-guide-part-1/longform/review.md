# 审校意见：有了工具站点子，别急着写代码：从需求验证到第一个用户（上）

## 总体评价

文章没有偏离选题卡，需求扫描、任务闭环、失败样本、搜索意图、变现取舍和七天清单之间的推进关系完整，MarkGleam 也确实被用作短案例，而不是写成开发流水账。当前主要风险不在结构，而在三处论证口径：个人开发速度被写成普遍能力、关键词量级缺少可追溯来源、功能询问被抬成了过强的付费信号；AI 写作观感整体偏低，但少量抽象比较级和过整齐的行动清单仍可收紧。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[开头第一句]** “AI 能在一小时内帮你做出一个能跑的工具”把 MarkGleam 的一次个人经历泛化成了 AI 对所有工具的稳定能力，“它不会告诉你”也把判断能力写成绝对缺失。正文能支持的是“作者这次大约一小时做出可用首版”，不能支持所有工具都能在一小时内跑起来。→ 建议：把钩子落回个人案例，例如“我用 AI 大约一小时做出了 MarkGleam 的可用首版，接下来两三天才开始回答它值不值得继续做。”如果希望保留普遍判断，可改成“AI 可能把首版压缩到几小时，但不会替你完成需求验证”。
2. **[“用搜索意图决定做什么”第二段]** “在当时的第三方工具估算里，`markdown to pdf` 的搜索量级明显高于 `markdown to image`”是全文最关键的外部数据判断，却没有工具名、查询日期、地区/数据库、截图或链接；参考资料中也没有这条数据的来源。选题卡已经写明它来自 2026-07-30 的 Semrush 快照，正文目前仍不可追溯。→ 建议：明确写成“我在 2026-07-30 查询 Semrush 的某地区/全球数据库时看到……”，补截图或可访问的结果记录，并继续保留“估算量不等于真实流量和付费需求”的限定；无法提供记录时，删去“明显高于”的事实断言，只保留“我因此把 PDF 列为待验证意图”。
3. **[“变现先选价值”末段]** “比价格页更可信的信号，是用户主动询问……”比较对象不成立：价格页本身不是信号，价格页访问、点击购买或提交付费意向才是行为信号；而询问去署名、批量处理或 API 只能证明功能需求，不能证明愿意付钱。这个表述会把产品需求错误升级为付费验证。→ 建议：改成“这些主动询问比凭空设计套餐更值得记录，但仍只是候选付费信号”，并补一句下一步要用价格访谈、带价格的候补名单、购买按钮或预售验证支付意愿。若原意是“不要先做完整价格页”，应直接写清楚，不要比较两类不同对象。

### 🟡 建议修改（影响表述质量）

1. **[MarkGleam 案例的前后衔接]** 前文把首版主流程定义为“导出图片”，后文直接出现真实用户“导出的 PDF 是黑的”，缺少 PDF 功能何时加入、为什么加入的时间节点。读者容易误以为一小时首版已经包含 PDF，或作者在尚未验证图片闭环时就扩了范围。→ 建议：在用户反馈案例前补一句最短的时间线，例如“图片版上线后，我又加了仍在试验的 PDF 导出；用户反馈发生在这个版本”，并说明 PDF 当时是否属于主流程。
2. **[“第一个真实用户”末段]** “一个失败样本……能证明你的任务闭环哪里是假的”仍然过强。单个样本能暴露一条可复现的失败路径，不能证明整个闭环的真实边界，更不能说明其他环境是否正常。→ 建议：改为“能暴露当前任务闭环在哪条路径上断了”或“能把一个模糊反馈变成可复现的失败路径”。
3. **[机会评分表]** “交付难度”这一列的分值方向与名称相反：越容易交付分数越高，读者按字面理解却会以为难度越高分数越高。其他四项都是“维度越有利，分越高”，这里只靠单元格内容才能纠正。→ 建议：将维度名改为“交付可行性”或“首版可行性”，保持整张表的方向一致。
4. **[快速发布段]** “现成域名只是后来才加的；没有域名并不妨碍……”表意不准：`github.io` 本身就是域名，后来增加的应是“自定义域名”或“独立域名”；“现成域名”也容易被理解成一开始就有。→ 建议：改为“自定义域名是后来才加的；没有独立域名并不妨碍把 `github.io` 链接发给第一批用户”。
5. **[最小观测能力末段]** “统计事件不要上传用户正文”是必要但不充分的隐私边界。文件名、页面 URL/查询参数、错误栈、导出尺寸和稳定标识也可能泄露内容或形成可识别记录。→ 建议：补一条很短的限定：“事件参数只记步骤、结果和必要环境信息；文件名、正文、URL 查询参数和原始错误内容先脱敏，能聚合就不留明细。”不用在本文展开合规讨论。
6. **[七天清单第 5 天]** “拿到一个成功样本和一个失败样本”被写成了按日必然发生的结果，但样本是否出现取决于触达量和用户行为，不是开发者单方面可完成的任务。→ 建议：改为“争取拿到……；如果还没有失败样本，继续做定向触达和观察，不要为了赶清单制造结论”。同理，七天后的三项产出宜写成目标而不是承诺。
7. **[全文多处比较级]** “一条更稳的上站路线”“判断下一步通常会更准”“顺序会稳很多”“三样更可靠的东西”连续使用“稳、准、可靠”，但没有始终说明比较基线。单独看不算禁词，成簇出现后会产生轻微 AI 摘要腔。→ 建议：保留一处作为主张，其余直接说结果，例如把“顺序会稳很多”改为“这样可以先验证付费价值，再承担支付和合规成本”。

### 🟢 可选优化（锦上添花）

1. **[“MVP 按任务闭环切”第三段]** “主题市场”不够自然，也可能被误解成内容题材市场；如果指可购买/下载主题的功能，建议改为“主题商店”。
2. **[真实用户案例]** “真的有人用了”口语自然，但信息量低于后文的具体故障。可直接改成“发布后，一位用户拿真实文件测试，并反馈 PDF 导出为黑图”，让案例更快进入有效信息。
3. **[参考资料]** 现有 GitHub Pages、Google doorway abuse 和 Search Console 链接能支撑对应能力与政策描述，建议在正文相应句尾就近挂链接，而不是全部堆在文末；这会让读者更容易判断哪些是官方规则、哪些是作者经验。

## 亮点

最值得保留的是“失败样本”部分：它给出了用户目标、原始文件、复现路径、根因线索和跨浏览器回归测试，具体程度明显高于常见的“多听用户反馈”。文章也多次主动限定结论——一个用户不等于市场成立、关键词估算不等于真实流量、三五次展示不能决定方向、变现方案仍是假设——这些限定有效压低了 AI 式过度确定和单案例外推的风险。整体结构虽然规整，但每张表承担的任务不同，暂时没有为了凑框架而重复同一观点的问题。
