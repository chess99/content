# 选题卡：有了工具站点子，别急着写代码：从需求验证到第一个用户（上）

## 核心洞察（一句话）

AI 已经把做出首版的成本压得很低，但工具站能不能继续做，仍要靠需求证据、完整任务闭环、真实用户反馈和搜索意图来判断；登录、支付和大而全的功能应该排在这些证据之后。

## 目标读者

有一个工具点子、能用 AI 辅助开发、准备第一次把产品放到公网，但还不熟悉市场扫描、MVP 切分、冷启动、SEO 和商业模式判断的个人开发者。

## 核心论点（5 条）

1. 写代码前先做一轮限时市场扫描，目标不是证明市场很大，而是确认问题真实、现有方案的缺口具体、第一批用户可以触达。
2. MVP 应按“输入—处理—结果—带走”任务闭环裁剪，不按功能数量裁剪；账号、支付、自定义域名通常不属于第一次验证。
3. 上线后的首要目标不是流量，而是让少量真实用户完成任务并交付失败样本；一个原始文件往往比几十条泛泛建议更有价值。
4. SEO 扩展应从搜索意图和真实产品能力出发；同义词归并，只有任务、默认状态或输出明显不同时才建新页面。
5. 变现方式应匹配用户价值、使用频率和持续服务成本；买断、订阅、广告和免费传播没有统一答案，支付系统不应早于付费信号。

## 推荐结构

1. 开头：为什么“一个小时做出首版”不等于“一个小时做成产品”
2. 先判断值不值得做：问题卡、市场扫描与机会评分
3. 做最小闭环并快速上线：功能取舍、部署、最少数据
4. 找到第一个真实用户：如何收反馈、为什么要拿失败样本
5. 用搜索意图决定下一步：关键词矩阵、页面边界与迭代优先级
6. 选择变现方式并给出七天行动清单；预告下篇的账号、支付和授权

## 潜在问题

- “先调研”容易被理解成做几周商业计划，需要强调限时、轻量，避免用调研拖延上线。
- MarkGleam 是单个案例，不能据此推出所有工具站都适合 GitHub Pages、买断或 SEO。
- “第一个用户”不是市场验证完成，只能证明流程有人愿意尝试。
- 关键词工具给出的是估算量，不等于真实流量，更不等于付费需求。
- 文章不能把首版开发速度写成成品速度；后续兼容、体验和运营才是主要工作。

## 事实与素材风险

- “一个小时”来自作者回忆，使用“大约”并明确仅指可用首版。
- “Markdown 转 PDF 是大词”来自 2026-07-30 的 Semrush 快照，只做相对量级案例，不把估算搜索量写成确定流量。
- GitHub Pages 默认域名、自定义域名和静态托管能力引用官方文档。
- 用户反馈、PDF 黑图和原始文件来自作者亲历与 Codex 会话记录，可以写成案例；不泄露用户内容。
- 变现价格、转化率和广告收入均未验证，正文不做收益预测。

## 渠道建议

- 博客：适合。可保留完整方法、表格、清单和来源链接。
- 公众号：适合。需要压缩 SEO 技术细节，强化案例和行动清单。
- 小红书：适合改造成 8—10 页“工具站七天验证路线”，不直接复用全文。
- 抖音：适合改成“首版一小时，后面三天都在做什么”的反差型口播，但不是本次范围。

## 选题结论

PASS_WITH_REVISION。题材常见，但“首版很快、判断更贵”的切口，加上真实用户失败样本、关键词决策和未实现的变现取舍，能避免写成泛泛的独立开发教程。正文必须坚持推荐流程，而不是按作者经历写流水账。
