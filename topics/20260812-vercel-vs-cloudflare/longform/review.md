# 审校意见：Vercel 还是 Cloudflare？独立开发者上站怎么选

## 总体评价

文章主线与选题卡一致：没有把平台对比写成无条件胜负，而是按运行环境、计费、文件和计算负载拆解，核心价格与限制也基本能在所列官方文档中找到。当前最需要修正的是几处仍把“依赖数量/项目类别”当成平台选择依据的表述，以及 Cloudflare 静态资源免费条件写得过宽；结构上同一组结论重复了三遍，可以明显收紧。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[结论速查表第 1 行；“运行环境”第 1、3 段；五个问题第 1 项]** 文中反复把“较多 npm 包”“原生模块”与优先选 Vercel 绑定，但包的数量不是兼容性指标，Vercel 支持全部 Node.js API 也不能推出任意原生二进制模块都可直接部署；具体包仍可能受构建平台、二进制目标、函数打包和体积限制影响。这会把本应逐项验证的条件写成平台能力结论。→ 建议：统一改成“明确依赖 Workers 尚不支持的 Node.js API，或已验证无法在 Workers/OpenNext 运行的依赖时，优先考虑 Vercel”；原生模块写成“需要在目标构建与运行环境实测”，不要把“包多”本身当判断条件。示例：`标准 Next.js，且已确认依赖完整 Node.js API 或 Workers 不兼容的包｜优先考虑 Vercel`。
2. **[“费用：月费只是第一行”第 2 段]** “静态资源请求免费且不限量”省略了产品与路由条件。官方口径是由 **Workers Static Assets** 直接提供的静态资源请求免费且不限量；SSR、`run_worker_first` 命中或其他实际执行 Worker 脚本的请求仍按 Workers 规则计费。当前表述容易让读者误以为经过 Worker/缓存的所有静态内容都免费。→ 建议：明确写成“由 Workers Static Assets 直接提供的请求免费且不限量；一旦路由先执行 Worker 脚本或做 SSR，仍计入 Worker 请求，CPU 仅在脚本实际运行时计费”，并让后文“内容站”的成本判断沿用同一条件。
3. **[“三类项目怎么选—第一个 SaaS”第 1 段]** “支付、邮件、鉴权和 AI SDK 较多，可以先看 Vercel”没有被研究资料支撑，也不是稳定的运行环境判断：不少此类 SDK 只依赖标准 Web API，在 Workers 上同样可用；反过来，单个不兼容依赖就可能决定平台。→ 建议：把 SDK 的“数量/类别”替换成验证结果。示例：`采用标准 Next.js，且支付、鉴权或 AI SDK 已确认依赖完整 Node.js 运行时，可以先看 Vercel；如果这些依赖支持 Workers/Web API，则不能仅凭 SDK 多得出该结论。`

### 🟡 建议修改（影响表述质量）

1. **[结论速查表第 2、3 行]** “内容站、目录站、计算器、轻量工具 → Cloudflare”和“文件流量多 → Cloudflare”仍按项目名称给答案，弱化了全文强调的条件化判断。尤其文件流量多直接支持的是优先评估 R2，不等于应用也应部署到 Workers。→ 建议：分别改成“静态资源占比高、动态逻辑轻 → 优先评估 Cloudflare Workers Static Assets”和“文件存储/分发量大 → 优先评估 R2；应用部署平台另按运行环境判断”。
2. **[“三类项目怎么选—图片、文件和下载类产品”第 1 段]** “最有价值的条件是……不是……”虽未原样使用“不是……而是……”，仍是同类否定式模板；这里不需要靠否定制造强调。→ 建议直接写事实：`图片、文件和下载类产品先评估 R2 的出口流量与操作费；这项判断不要求应用运行在 Workers。`
3. **[全文结构：速查表、三类项目、五个问题]** 同一组选择结论出现三遍：开头表格已经给答案，81—99 行按三个场景复述，101—115 行又按问题复述。删掉其中一组不会影响理解，反而能突出真正有信息量的运行限制和计费条件。→ 建议：保留“速查表 + 五项差异 + 五个问题”；把“三类项目”压缩为 1—2 个有冲突条件的案例，例如“Next.js 应用 + R2 文件”，用来展示组合判断，而不是再次枚举同样结论。
4. **[“轻后端两边都行”第 3 段]** “HTTP 请求的墙钟时间没有固定硬上限，只要客户端仍保持连接”基本符合 Workers 文档，但容易被读成可稳定依赖的长任务保证；同一官方限制页还说明运行时更新会给在途请求约 30 秒宽限，客户端断开也会取消相关任务。→ 建议补一句边界：`这不等于适合无限长任务，连接中断、运行时更新和 CPU/内存上限仍会终止执行；需要可靠长任务时应使用专门的异步任务机制。`
5. **[参考资料与正文数字段落]** 文末列出了官方链接，但正文里价格、内存、CPU、时长等密集数字没有就近标注对应来源，读者必须自己猜哪一条文档支持哪句话。→ 建议：至少在每个数字段落末尾加对应官方链接或脚注；尤其把 Vercel 4.5 MB、Workers 128 MB/5 分钟、Vercel 800/1800 秒分别挂到具体限制页。对 1800 秒再写清适用运行时/启用条件，避免“特定运行时”悬空。
6. **[“内容站、目录站、计算器和轻工具”第 2 段]** `留在 Vercel同样合理` 缺少空格，是明显排版错误。→ 建议改为 `留在 Vercel 同样合理`。

### 🟢 可选优化（锦上添花）

1. **[开头第 3 段]** “下面把这几条判断展开”只是流程提示，没有新增信息。→ 建议直接进入“运行环境”小节。
2. **[“费用”第 4 段]** “单页价值不高”与平台成本没有直接可计算关系，也容易让读者停下来猜含义。→ 建议换成可观察条件，如“静态页面多、单页请求量大、动态计算少”。
3. **[术语一致性]** `Node.js compatibility`、`active CPU`、`isolate`、`wall-clock` 中英文混用。技术读者能理解，但首次出现时用一句中文解释会更顺，例如“Node.js 兼容层”“活跃 CPU 时间”“隔离实例”“墙钟时间（含等待的总耗时）”，后文保留英文名即可。

## 亮点

开头两句直接给出“答案取决于技术、流量、文件与计算”的判断，符合选题卡和开头规则。文章对 Hobby 非商业限制、R2 仍收存储与操作费、Workers CPU 时间与墙钟时间的区别，以及“Vercel 应用 + R2 文件”的混合方案都交代了边界；这些内容具体、可操作，也避免了“Vercel 一定省事”“Cloudflare 全面更便宜”一类先验结论，建议保留。
