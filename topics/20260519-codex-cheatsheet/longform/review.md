# 审校意见：Codex CLI 速查手册：从交互对话到 CI 自动化的全部命令

## 总体评价

文章结构清晰、命令覆盖全面，对有 Claude Code 经验的读者确实友好，对标文章的定位准确。主要问题集中在两处：TL;DR 的自我指涉读不通；以及末尾"和 Claude Code 的关键差异"一节有一处技术表述存疑，需要核实。其余是一些表述和结构的小毛病，整体质量不错，修完可以发。

---

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[TL;DR]** "对应 Claude Code 的那篇写 Codex"——读者不知道"那篇"指什么，语义残缺。这句话的语序也混乱（"对应……的那篇写 Codex"说不通）。  
   → 建议改为："这是一份 Codex CLI 的实用命令速查手册，与博客里已有的 [Claude Code 速查手册](/posts/claude-code-cheatsheet/) 对应。"直接给链接，问题彻底消除。

2. **[和 Claude Code 的关键差异 — 审批模型不同]** "Codex 的沙箱是操作系统级隔离（macOS Seatbelt / Linux Landlock），Claude Code 的是应用层控制"——这个对比本身是一个较强的技术主张，但文章没有给出来源，也没有解释"操作系统级"具体意味着什么（能防什么、不能防什么）。若读者较真去查，发现 Codex 在非 macOS/Linux 环境下行为不同，或者 Landlock 支持有版本限制，会觉得被误导。  
   → 建议：要么补一句说明 OS 支持条件（"macOS 上用 Seatbelt，Linux 上用 Landlock，Windows 暂无 OS 级隔离"），要么软化表述为"Codex 的沙箱在支持的平台上做到 OS 级隔离……Claude Code 的权限控制是应用层的"。

---

### 🟡 建议修改（影响表述质量）

3. **[第一组 — 启动交互会话]** 正文里描述了 `Tab`、`Enter`、`@` 等快捷键，末尾的"快捷键速查表"里这些内容重复出现。文章两处都有，增加了篇幅，但没增加信息量。正文里那段的价值是给上下文解释，表格的价值是速查。  
   → 建议：正文保留解释性描述，表格新增 `Ctrl+O`（复制输出）和 `Ctrl+L`（清屏）等正文没有详细说的条目，已在正文出现的可以在表格里保留但减少正文的重复叙述，使两者互补而非重复。

4. **[第二组 — `/compact`]** "用 `/status` 看到 token 接近上限时"——读者可能没有"接近上限"的直觉，不知道多少算接近。  
   → 建议补一个量级参考：比如"上下文用了 70-80% 以上时"，让"什么时候用"更可操作。

5. **[组合使用示例 — 开发新功能的标准流程]** 流程用的是纯文本编号列表，不是代码块，但和上下的 bash 代码块格式不统一，视觉上稍显随意。更关键的是第 4 步"Tab 排队指令"写得像是操作动作的说明，但放在编号流程里看起来像是命令，容易让读者困惑。  
   → 建议第 4 步改为更明确的语言，比如"在 Codex 执行时用 Tab 排队下一条指令，不要打断它"。

6. **[第三组 — Execpolicy]** 节标题 "Execpolicy — 规则文件控制命令白名单"里的"白名单"其实表述不完整，规则文件同时控制允许/需要确认/禁止三种状态，不只是白名单。  
   → 建议标题改为"Execpolicy — 规则文件定义命令权限"或"——精细控制命令权限"。

---

### 🟢 可选优化（锦上添花）

7. **[文章标题]** "从交互对话到 CI 自动化的全部命令"——对标的 Claude Code cheatsheet 标题是"从入门到自动化的全部命令"，两篇并列读有点像在比谁的副标题更长。Codex 这篇标题可以更有个性，或者突出 Codex 独有的点（如 `cloud`、`fork`、多沙箱等）。不改也不影响阅读，但改了能让两篇文章在列表里更容易区分。

8. **[第八组 — Codex Cloud]** `--attempts 3` 这个用法（并行跑多次取最好）是 Codex 差异化能力里很有意思的一个，但在这一节只用了两行带过。"取最好的结果"是怎么判断的？是 Codex 自己选，还是需要人工介入？读者会好奇。  
   → 建议加一句解释评估机制，哪怕是"Codex 自动评估三次结果，选质量最高的一个"，或者诚实说"目前需要你自己 `codex apply` 选一个"。

9. **[末尾差异对比节]** 这一节放在文章最后，是全文最有观点、最不像"手册"的部分。它完全可以作为引导读者继续读的"为什么两者我都该了解"的铺垫，但目前是压轴的——读者如果是来速查命令的，可能看不到这里。  
   → 可选：把差异对比提前到 TL;DR 后面，作为"读前预设"，或者在文章引言里加一句提示"文末有和 Claude Code 的关键差异对比"。

## 亮点

- **"什么时候用"段落** 几乎每一节都有，且写得具体（"开发持续多天的功能时，每天用 `--last` 接着昨天进度"），这是 cheatsheet 类文章里最难写好的部分，这篇做到了。建议这个模式推广到博客其他工具类文章。

- **`--yolo` 一节的处理方式** 简短、诚实、不猎奇，"只在已经做好硬隔离的环境里用"是准确的建议，没有夸大也没有回避。

- **末尾差异对比节** 是文章里最有价值的原创内容，覆盖了 OS 级沙箱、fork 工作流、云端任务、配置格式四个实质差异，对已用 Claude Code 的读者有真正的参考价值。
