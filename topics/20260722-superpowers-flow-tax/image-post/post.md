# Codex 给我写小红书文案，做起了 TDD

前几天，我让 Codex 帮我写一篇小红书文案。

它自动加载了 Superpowers，然后开始写计划、拆任务、做 TDD。

写文案，搞 TMD 的测试驱动开发。

人类干不出这种事。

我当时发帖吐槽，后来有人真的用同一个模型、同一个推理档位，对 Superpowers v6.1.1 做了隔离 A/B。

三项隐藏评测里，两边正确率都是 3/3，没有测出效果提升；但 Superpowers 版本：

- 耗时约 3.61 倍
- 输入 token 约 8.98 倍
- 输出 token 约 2.74 倍

其中一项并发 bug 修复，基线用了 139 秒、约 13 万 input tokens；Superpowers 用了 552 秒、约 157 万 input tokens。

当然，这仍然只是小样本，不能直接推出“Superpowers 已经没用”。作者自己公布的“快 50%、便宜 60%”，比较的也是 v6 和旧版，不是 Superpowers 和裸模型。

但它至少把我原来的不适感说清楚了一部分：

问题不是有没有流程，而是有没有比例尺。

Superpowers 的规则很激进：只要有 1% 的可能适用，也必须调用 Skill。这个设计在模型经常漏步骤、不写测试的年代很有价值；放到现在的 Codex 里，却可能把一篇文案也拉进完整的软件开发流程。

我猜有两个原因：

第一，Codex 的定位变了。以前它更像代码开发工具，现在已经是一个能研究、写作、操作文档和浏览器的通用智能体。遗留下来的软件工程流程，开始和大量非代码任务错配。

第二，模型进步太快。以前需要 Skill 补上的计划、审校、子任务和验证能力，现在不少已经进入模型或产品本身。过去是在补课，现在有些 Skill 开始重复收学费。

这不代表所有 Skill 都该删。

真实工具、私有上下文、确定性检查和专业判断依然值钱。最值得重新审视的，是那些试图接管所有任务的通用工作流。

一个好 Skill 不只要知道什么时候启动，还应该知道什么时候闭嘴。

你现在还常驻安装 Superpowers 或 gstack 吗？
