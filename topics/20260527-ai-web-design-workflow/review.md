# 审校意见：让 AI 写出好看的网页，不是多写几个高级形容词

## 总体评价

文章方向和选题卡一致，核心论点清楚：把模糊审美拆成 agent 能讨论、执行、验收的约束。当前稿件的问题不是“读不下去”，而是有几处关键论证还停留在经验判断层面，外部工具段落也需要补出处和边界，否则容易被读者理解成工具清单或 AI 设计平台综述。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[“业界还有另一条路线：先设计，再写代码”第 98-104 行]** 这里集中写了 Figma Make、Figma Sites、Stitch、Lovable、Webflow 和 Figma AI Report，但没有任何出处标注。尤其是“78% 提升效率 / 32% 可以依赖 AI 输出”“Figma Make 的 functional version 不能直接进入 Figma Design”等属于可核验事实，读者无法判断来源，也无法区分官方说法和作者转述。→ 建议：给这些事实加官方链接或脚注；如果不想加太多链接，至少把段落拆成“官方能力”和“我的判断”两层。示例方向：“Figma 官方在 2025 AI Report 里给过一组数字……这个数字支持的是‘AI 加速产出’，不是‘AI 替代质量判断’。”

2. **[“这件事不是一次 prompt 搞定的”第 23 行，以及第 37、47、67 行]** 文章反复说三个 skill 分别负责 brainstorming、视觉、交互，但没有展示 skill 到底比普通 prompt 多了什么。选题卡已经预判读者会质疑“这只是换了几个 skill，和 prompt engineering 有什么区别？”，当前稿件还没有正面回答。→ 建议：补一个很小的对比块：普通 prompt 长什么样，skill 化之后多了哪些固定检查项、角色边界或验收步骤。重点不是贴完整 prompt，而是说明 skill 的价值在于可复用的流程约束，而不是“更会写形容词”。

3. **[第 81 行“后续的几次提交其实都在磨这些问题”]** 这里用 bottom nav、book header mode、返回路径、首页导航简化支撑“ui-ux-pro-max 能把页面磨到能用”，但只列名称，没有说明具体问题、修改动作和用户体验变化。论据目前太像内部 commit list，外部读者无法感知“磨”在哪里。→ 建议：挑 1-2 个例子写实，例如“底部导航从哪些项变成哪些项，解决了什么路径问题”“book header mode 在小屏幕上避免了什么挤压”。不需要展开成很长案例，但要让读者看到因果链。

4. **[第 96-102 行“另一条路线”]** 这一节把 Figma、Stitch、Lovable、Webflow 放在同一条“先设计，再写代码”的路线里，但这些工具的定位并不完全一样：Figma/Make 更偏设计工作流和原型，Stitch 更偏 UI 生成画布，Lovable 更偏应用生成，Webflow 更偏站点构建与设计系统落地。现在的写法容易把不同层级的工具合并成一个趋势，逻辑上有点粗。→ 建议：用一句话承认它们不在同一层：“这些工具不完全同类，但共同点是把设计判断前置到画布、组件和 tokens 里。”这样可以保住论点，同时避免以偏概全。

### 🟡 建议修改（影响表述质量）

1. **[第 21 行前后对比图说明]** 这段描述“纸张质感、卡片层级、横向书架和底部导航形成了更统一的阅读应用气质”，方向是对的，但还偏形容。→ 建议：多给 2-3 个可观察指标，例如首屏信息优先级、主要操作距离、分类入口数量、移动端触摸区域。这样能和后文“可执行约束”形成呼应。

2. **[第 57 行“安静的书房”]** 这个比喻有效，但如果只停在“米白底、纸张颗粒、偏暖品牌色”，还是容易滑回视觉风格描述。→ 建议：补一句它如何影响信息架构或组件选择，比如“所以首页不做巨大 hero，而是把继续阅读和可浏览书架提前”。这能证明“气质”不是装饰，而是设计判断。

3. **[第 79 行规则列表]** “Accessibility、Touch & Interaction、Layout & Responsive……”这一串中英混排略像工具说明书，和全文口语化风格有一点断裂。→ 建议：可以保留英文分类，但后面用中文解释并压缩，例如“它会盯住触摸目标、导航项数量、横向滚动、当前状态这些基础红线”。读者更容易吸收。

4. **[第 98 行 Lovable 段落]** “Lovable 的官方文档则反复强调一件事：模糊输入会得到模糊输出……”这句话判断合理，但“反复强调”略泛。→ 建议：要么加具体文档链接，要么改成更稳的表述：“Lovable 文档里关于规划、组件拆分和真实内容的建议，指向的是同一个原则：输入越具体，结果越可控。”

5. **[第 118 行“不要让同一个 agent 刚写完就宣布自己做得很好”]** 这句很好，但可以更落地。→ 建议：补一句具体做法，比如“换一个审校角色，只看截图和交互路径，不看实现过程”。这会让结尾前的建议更可执行。

### 🟢 可选优化（锦上添花）

1. **[标题]** 当前标题有观点，也贴合文章。可以考虑更直接地突出工作流收益，例如“让 AI 写出好看的网页：把审美拆成可验收的约束”。现标题更有口语感，改不改取决于发布渠道。

2. **[第 83-90 行四步工作流]** 这里已经是文章的骨架，可以做成一个更醒目的小节或列表，并在每一步后补一句“产物是什么”：方案取舍、视觉约束、交互检查、截图验收。这样读者读完更容易照着做。

3. **[全文]** 目前没有触发写作指南里的禁用词，开头也符合“直接给问题/结论”的要求。可以继续保持这种口语化技术分享风格，不需要改成更正式的教程腔。

## 亮点

开头从自己的站点前后对比切入，比泛泛讨论“AI 设计趋势”更可信。文章最值得保留的是“三个角色分工”的结构：先问问题，再定视觉，再磨交互，这个框架确实能把“好看”从主观形容词变成可执行流程。结尾“AI 不天然拥有你的品味”也很准确，能把全文从工具推荐拉回人的判断。
