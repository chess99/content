# 审校意见：Skill 的整洁之道

## 总体评价

文章整体论证方向是成立的，用具体案例带出原则的写法有效。但存在几处较严重的问题：对 Conway's Law 的理解和引用有偏差，部分论断在逻辑上跳步，以及一处 SOLID 原则的映射存在偷换概念。

---

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **[Conway's Law 一节]** Conway's Law 的方向被反转了，且反转后的结论并未被充分证成。

   原始定律的方向是：**组织沟通结构 → 系统架构**（组织决定架构，这是被动的、难以避免的）。文章写道"你怎么组织 agent 团队，决定了系统的架构"，然后建议"如果你想要一个什么样的系统架构，就先想清楚你要组建一个什么样的 agent 团队"——这是把 Conway's Law 当成一个可以主动利用的设计工具，实际上更接近 **Inverse Conway Maneuver**（逆康威操作），这是一个独立的工程实践概念，与 Conway's Law 本身是反向的。

   更大的问题：Conway's Law 成立的原因是**跨组织边界的沟通成本高**，所以接口自然沿组织边界形成。但 agent 之间没有沟通成本的障碍，Conway's Law 的成立前提在这里根本不适用。文章把一个描述人类组织沟通摩擦的规律，不加论证地搬到了 agent 系统上，这个类比是跛脚的。

   **建议**：要么不用 Conway's Law 这个框架，直接说"agent 分工方式决定系统架构形态"；要么用 Inverse Conway Maneuver 的概念并说明它与原定律的区别；要么正面论证为什么 agent 系统中 Conway's Law 仍然适用（比如：设计者的思维模型是人类组织的映射，这个人类因素仍然存在）。

2. **[SOLID 一节，"依赖倒置"部分]** 对 DIP 的映射存在概念模糊。

   文章把"`.check-work/cases.json` 的文件路径和格式约定"称为"抽象"——在面向对象语境里抽象是接口/抽象类，在这里"抽象"是一个文件格式约定，两者跨越较大。文章在解释时含糊带过，与后面"这是旧知识的新应用"的立意冲突——新应用就要说清楚概念如何迁移，否则让有技术背景的读者皱眉。

   **建议**：明确说明"DIP 里的'抽象'在 skill 场景中对应的是数据格式约定（schema）和文件路径协议"，而不是直接借用"抽象"一词。

3. **[Planner-Generator-Evaluator 案例]** "Anthropic 工程师在设计多 agent 编程系统时，用了 Planner-Generator-Evaluator 三角"——此处应标注来源或说明依据。

   这个命名框架并不是广为人知的标准术语，读者无法核实。如果是作者对某篇文章的总结归纳，需要注明；如果是作者自己的提炼，不应以"Anthropic 工程师……用了"这种方式表述。

   **建议**：加上具体来源链接，或改为"类似 Anthropic 在某某文章中描述的……"，或改成"这种分工模式可以类比为 Planner-Generator-Evaluator 三角"（归为作者自己的归纳）。

---

### 🟡 建议修改（影响表述质量）

1. **[开篇第二段]** "AI 能写出比大多数人更整洁的代码"这个论断被当作公理使用，但这是有争议的。AI 生成的代码在局部函数层面可以很干净，但在结构层面经常引入隐患。放在开头，对挑剔的读者是减分的。

   **建议**：改为更有限度的描述，例如"在函数和命名这个层面，AI 的输出已经相当稳定"。

2. **["接口隔离"部分]** ISP 的映射是所有 SOLID 原则里最牵强的。ISP 讨论的是接口粒度问题，而文章映射成"传给 skill 的上下文要精简"，更准确对应的是**最小权限原则**或**精简上下文设计**，而不是 ISP。

   **建议**：选择映射最自然的三四条（SRP/OCP/DIP），剩下的单独展开，反而更有说服力。

3. **["技术架构服务于组织架构"一节]** "领导才是真正的架构师"被归为《架构整洁之道》的洞察，但书中原意更接近"架构师必须是能影响组织的人，否则架构决策无法落地"——强调的是架构师需要有组织影响力，而不是"领导才是真正的架构师"。后者会让读者误以为技术架构师不重要。

   **建议**：更准确地转述原意，或不归因到《架构整洁之道》，直接表达作者自己的观点。

---

### 🟢 可选优化

1. **["渐进式细化"部分]** 这一段和 SOLID 原则没有对应关系，放在"把架构原则翻译到 skill 层面"章节下结构不一致。建议移入后面的"具体范式"章节。

2. **[全文]** "skill"这个词承担了多种含义（Claude Code 的 slash command、泛指封装好的 AI 能力单元、agent 执行的任务类型）。对不熟悉 Claude Code 工具链的读者，建议在第一次使用时给一句话定义。

---

## 亮点

"一个 skill 做了两件事，你会在两周后感受到痛苦：测试平台接口变了，你发现要改三个 skill"——这个即时反馈的描述非常有说服力，把抽象原则和具体痛苦对应起来，是全文最好的一段。

`test-case-fetcher` / `code-checker` 拆分的案例贯穿全文作为锚点反复使用，比泛泛举例有效得多，这个叙事结构值得保留。
