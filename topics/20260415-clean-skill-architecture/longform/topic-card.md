# 选题卡：《Skill 的整洁之道：软件架构原则在 AI 时代的新生》

## 核心洞察（一句话）
AI 时代程序员的工作单元从"函数/模块"变成了"skill/agent"，但整洁架构的底层逻辑没变——Conway's Law 依然成立，只是组织的粒度从团队缩小到了个人。

## 目标读者
正在用 Claude Code、Cursor、Copilot 等 AI 工具扩展工作边界的中高级程序员；对"AI 如何改变开发者角色"有切身感受但还没系统化思考的人；有过 multi-agent 实践或计划尝试的技术 lead。

不适合：纯管理者（缺乏 skill 实操背景）、初级开发者（认知跳跃太大）。

## 核心论点
1. 程序员的 scope 正在从"写代码"扩张到"编排 AI 完成整个研发流程"，skill 是新的工作单元。
2. 旧架构原则（SOLID）在 skill 层面依然适用，且有直接的操作指导意义——单一职责防止 skill 腐化，开闭原则让 skill 可复用而不被改坏。
3. 多 agent 协作本质上是一种组织结构，Conway's Law 在这里仍然成立：你的 agent 架构会镜像你的思维分工方式。
4. 技术架构服务于组织架构这一规律，在个人 AI 工作流层面同样成立——skill 的边界划分，其实是个人认知分工的外化。

## 推荐结构
1. 开篇锚点：一个具体的 skill 拆分决策（test-case-fetcher 那个例子），引出"这不就是单一职责吗？"的顿悟感
2. 转折：程序员的 scope 在扩张，但扩张之后发现遇到了同样的老问题
3. 主体：架构原则逐一翻译（SRP/OCP/DIP 为主，ISP 酌情）
4. 升维：从 skill 架构到 agent 组织，Conway's Law 出场
5. 收尾：旧知识在新载体上的投影——会用旧知识的人，在 AI 时代有结构性优势

## 潜在问题
- **质疑1**："AI 时代还需要架构吗？AI 自己会整理。" → 需正面回应：skill 集混乱会让 AI 反复犯同类错误，这是实践中可验证的。
- **质疑2**："类比是否牵强？skill 和模块根本不是一回事。" → 用具体例子让类比落地，test-case-fetcher 是好锚点。
- **质疑3**：Conway's Law 延伸到个人工作流，是否过度诠释？ → 这是全文最弱的一环，需要具体案例支撑。
- **质疑4**：原则列举有凑数感。ISP 映射不如 SRP/OCP/DIP 自然，没有好例子应删去。

## 渠道建议
- **技术深度版（博客/内部知识库）**：保留完整原则翻译和架构范式章节，逻辑严密比流畅更重要。
- **同源多渠道**：深度文章直接多渠道发布，不需要轻量化改写。

## 选题结论
**PASS_WITH_REVISION**

洞察成立，目标读者清晰，时效性强。核心问题是论点密度过高——SOLID 四条 + Conway's Law + 组织架构类比同时出现，容易让读者觉得"什么都讲了，但什么都没讲透"。建议 SRP 用详细案例讲透，其余点到为止，形成主次。

## 对比现有文章的评估

**做得好的地方：**
- test-case-fetcher 拆分作为开篇锚点，接地气，可信度高。
- Conway's Law 出现在 agent 层面是全文最有新意的一笔，值得加重。
- "这不是新知识，是旧知识的新应用"作为收尾，定调准确。

**可以改进的地方：**
1. **原则章节太平铺**：SRP/OCP/DIP/ISP 四条并列，读完容易记不住任何一条。建议 SRP 用详细案例，其余一两句话点到为止。
2. **Conway's Law 段落潜力最大但目前最薄**：缺少"agent 架构镜像了我的什么思维分工"的具体叙述，补一个真实多 agent 协作案例可成为传播爆点。
3. **"技术架构服务于组织架构"一节在个人工作流场景下说服力需补强**：从公司组织架构跳到个人 skill 划分跨度较大，建议用"个人认知分工的外化"这个角度过渡。
