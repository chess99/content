# 审校意见：DEX 拆出来以后，我把反编译源码恢复成了能跑的 Android 工程

## 总体评价

文章成立。开头很早就交代了可见结果和“只恢复核心离线链路”的边界，正文也按资源、依赖、Manifest、控制流、设备验收的实际依赖顺序推进，案例没有被写成完整复刻。当前主要缺口不在主线，而在技术教程的可复现度：几个最关键的修复步骤仍停留在经验概述，读者能理解为什么出错，却不总能据此判断下一步具体该做什么。

## 真机共存事故后的二次审校

文章初稿完成后又发生了一次安装隔离事故，随后补做了模拟器与真机验收。二次审校确认以下修订已经进入博客稿与渠道无关终稿：

- 没有沿用“Android 开发版天然会覆盖正式版”的经验说法，而是把 applicationId 与签名的三种安装结果分开说明。
- 没有把真机事故武断归因为覆盖。事后检查时原版和目标恢复包都不在，证据不足以还原中间操作，只能确认原有验收缺少“原版仍在”的硬断言。
- 增加了可复现的 `INSTALL_FAILED_DUPLICATE_PERMISSION` 案例，说明恢复包改了 applicationId 后，硬编码的原版自定义权限仍会阻止两版共存。
- 增加 `${applicationId}.permission.*`、`${applicationId}.fileprovider`、独立显示名，以及 `pm list packages` 同时列出两包的通过信号。
- 补充安装前备份原版数据的提醒，明确重新安装 APK 不会自动恢复已经删除的应用沙箱数据。

新增内容与恢复仓库 `c2be7c5`、原版 APK 指纹、模拟器双包安装结果和真机双包安装/冷启动结果一致。没有新增发布阻断项。

## 问题列表

### 🔴 发布阻断

无。

### 🟡 编辑建议

1. **[“613 个 Java 文件还不叫 Android 工程”至“先让公共依赖回到构建系统”]** NinePatch 一节列出了 8 个失败文件，也解释了 APK 资源是合并结果，但没有给出 AAPT2 的实际错误信号、这 8 个文件最后如何处理，以及怎样判定某份解码资源应由 AAR 接管还是继续留在应用模块。后文一句“AAR 正好接住前面暴露的资源问题”跨过了读者最需要复现的一步。→ 建议：选这次真实处理中的一条最小链路，写清“报错文本或特征 → 资源归属判断 → 实际移动、排除或替换动作 → 下一次构建的预期结果”；同时说明遇到应用自定义覆盖同名依赖资源时不能按前缀整批删除。

2. **[“先让公共依赖回到构建系统”的旧 R 类代码块]** 正文说“排除了目标包下的旧 R 类”，示例却只匹配 `R$*.java`。若反编译目录里还有顶层 `R.java`，它不在这个模式内；代码块也没有说明应放在模块的 `build.gradle.kts`，且 `JavaCompile` 是否需要显式 import。按当前写法复制，读者可能仍遇到重复 `R` 类。→ 建议：按真实目录说明本次是否存在 `R.java`；若存在，补齐排除范围。给出代码所在文件、必要 import、执行任务和通过信号，避免把只对本次文件形状成立的片段写成完整方案。

3. **[“编译器开始检查反编译质量”至“没有异常桩也不代表方法都在”]** Kotlin 默认参数桥接、展开的 suspend 调用和缺失 `onCreate` 是全文最有价值、也最难迁移的部分，但现在只有处理原则。Activity 代码还是“简化后的常见形状”，没有明确标注为示意代码；读者也看不到一个真实错误怎样由字节码、调用方和原应用行为共同约束到可验证实现。→ 建议：只选一个代表性缺口做小型闭环即可，例如一处 `launch$default` 或一个 Activity 入口，展示原始编译/运行错误、核对材料、修复后的调用形状和回归断言；若不能公开具体源码，就明确标成伪代码并保留方法签名与验证信号。

4. **[开头、控制流修复段和“这次恢复停在哪里”]** `18,027`、`613`、`8`、`9`、`17`、`4`、`5`、`56` 等数字承担了案例可信度，但正文没有给出扫描口径或可追溯记录。其中结尾“17 个明确业务异常桩与 4 个富文本残缺方法”还会让人不确定这 4 个是包含在 17 个之内，还是另有 4 个。→ 建议：用一小段后台材料说明或附录表写清每个关键计数的对象、扫描方式和记录来源；至少明确“17 与 4”的包含关系，以及“56”是补回 5 个之后的剩余数。无需分发 APK、DEX 或目标应用源码，也能让这些结果可核验。

5. **[“把壳入口换回业务 Application”中包名隔离段]** “签名不同无法让两个相同包名的应用共存，所以使用新的 applicationId”把两个限制混在了一起。Android 本来就不会把相同 application ID 的两个应用当成可共存应用；签名不同进一步意味着恢复包也不能作为原包的更新安装。→ 建议：把因果关系拆清楚，说明“为了共存必须改 applicationId；原签名不可用也意味着不能覆盖更新原包”，以免读者误以为同签名时相同包名可以并存。

6. **[“我怎样验收一个恢复工程”的日志检查]** 表格写的是“扫描目标进程日志”，给出的命令却对整个设备的 `logcat -d` 做关键词搜索，而且 `timed out` 范围很宽。设备上其他进程的异常会造成假阳性；目标进程若中途重启或退出，单纯“没有命中”也容易被误读为通过。→ 建议：要么把表述改成“扫描本轮设备日志并人工确认归属”，要么按 PID、UID 或明确 tag/package 收窄，并写出进程退出时的检查方向。保留正文已有的提醒，即日志无命中不能替代页面断言。

7. **[“我怎样验收一个恢复工程”的数据初始化层]** `run-as ... ls -l databases` 只能证明数据库文件、WAL 和 SHM 已创建，不能证明 Room schema、迁移结果或核心数据已经正确初始化。它与表格里的“数据初始化”通过信号并不完全等价。→ 建议：增加一个最小内容断言，例如 schema version、必需表是否存在，或完成一次编辑保存后查询到预期记录；如果本文只准备验证“数据库已打开”，就把这一层的名称和结论相应收窄。

### 🟢 可选优化（锦上添花）

1. **[第一处命令之前]** 运行环境到验收末尾才出现，而前文已经给出 Kotlin DSL、PowerShell、`aapt`、Gradle 和 adb 命令。→ 建议：在首个代码块附近放一行前置条件，说明 Windows PowerShell、模块脚本类型、JDK/AGP/Gradle/compileSdk、Android SDK 环境变量和 API 34 x86_64 模拟器；末尾继续保留“本次实际版本”作为结果记录。

2. **[全文结构]** 读者任务包含“判断工程卡在哪一层”，正文已经有足够材料形成更直接的诊断入口。→ 建议：在验收表前后补一个很短的映射，例如“AAPT2 报错看资源边界、duplicate class 看依赖边界、启动即退出看 Application/Manifest、页面打开才报 JNI 看 native 入口、能显示但行为不对看控制流”，帮助读者把案例快速迁移到自己的工程；不必再扩写新的背景知识。

## 亮点

- 开头先给可见结果，再立刻限定“核心离线功能”而非完整恢复，标题承诺与事实边界一致。
- `recovered/` 保存原始证据、`legacy-app/` 保存可构建改动的分层非常实用，也自然解释了逆向恢复中为什么要保护证据链。
- “不把剩余 native 入口填成空页面来增加完成率”是很有作者判断的一段，既具体，也把“能跳转”和“功能恢复”区分开了，建议原样保留。
- 黑盒对照的时间刻度/时间网格例子说明了静态代码与行为参照各自能回答什么问题，是全文最容易被记住的案例之一。
- 验收从干净构建、安装隔离、冷启动一直走到数据库、核心操作和日志，且主动说明单一信号不能证明完成，方法意识是扎实的。
- 整体语言自然、判断明确，没有明显的模板化总结、空洞拔高或为显得谨慎而连续堆叠限定语；结尾“构建系统和设备回答”也承担了全文判断，不是额外升格。
