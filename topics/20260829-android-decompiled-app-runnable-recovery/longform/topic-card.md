# 选题卡 DEX 拆出来以后怎样恢复成可运行 Android 工程

## 文体与读者任务

- 文体类型：技术教程
- 读者任务：读者已经拿到可读的运行时 DEX 或 JADX 输出后，能够判断工程卡在资源、依赖、Manifest、反编译控制流还是运行验证，并据此把目标范围内的离线功能恢复到可构建、可安装、可冷启动的状态。

## 文章主线

以一次加固 Android 应用的真实恢复过程为样本，说明从反编译结果到可运行工程之间缺少哪些构建信息、怎样逐层补回，以及什么证据才足以宣称核心链路已经能运行。

## 目标读者

具备 Android 构建、APK 分析或基础逆向经验的人。他们已经越过“静态 JADX 只见壳”的阶段，手里有业务 DEX、资源和 Manifest，却发现这些材料无法直接组成 Android Studio 工程。

## 支撑单元

1. 上一轮动态拆壳得到 6 个相关 DEX、613 个目标包 Java 文件，但恢复快照无法构建。
2. 第一次资源编译在 8 个已解码 NinePatch 上失败，暴露 APK 资源与源工程资源的差别。
3. 通过类命名空间、资源前缀、调用关系和公开 Maven 坐标重建依赖边界，避免把 AndroidX、Kotlin 和公开 SDK 的反编译代码当作业务源码编译。
4. 从 Manifest 中移除壳启动入口，恢复真实 Application，并使用独立 applicationId 隔离恢复工程与原应用。
5. 处理旧 R 类、Kotlin 默认参数桥接、展开协程和 17 个明确反编译失败的方法体。
6. 发现并补回 5 个核心 Activity 入口，同时记录仍存在的 56 个 native `onCreate`，说明异常桩扫描不能代表恢复完整度。
7. 用干净构建、清数据冷启动、数据库落盘、核心页面、编辑保存和日志扫描逐层验收。

## 推荐结构

1. 上一篇结束以后，手里到底有什么
2. 为什么 613 个 Java 文件仍然不是一个工程
3. 先处理资源和依赖边界
4. 再恢复启动入口与包名隔离
5. 编译错误怎样暴露反编译缺口
6. 用原应用行为补控制流
7. 怎样证明工程已经能跑
8. 当前恢复边界

## 潜在问题

- “可运行”容易被理解成完整复刻，正文必须尽早说明当前只覆盖核心离线链路。
- 依赖版本来自兼容性重建，不能写成已经精确还原原 Gradle 配置。
- 文章不能分发目标应用源码、APK 或 DEX，只展示通用方法、错误类型、目录策略和验证命令。

## 事实与素材风险

- 文章中的文件数、方法数、Activity 数和验证结果必须以恢复仓库文档、源码扫描与真实构建记录为准。
- NinePatch 的描述只写本次 AAPT2 失败和处理策略，不把一个样本扩大为所有 APK 解码工具的必然行为。
- Android Gradle 与资源机制如需外部定义，优先使用 Android 官方文档，不凭印象补充。
