# 审校意见：Codex Goal：长期任务要先写完成条件

## 总体评价

文章选题成立，主线也和选题卡一致：它没有写成命令手册，而是在回答“什么任务值得开 Goal、怎么写才不失控”。目前最大问题不是结构，而是几处产品事实和机制对比写得太像确定结论：读者会把作者的使用经验、官方文档描述、以及对实现机制的推断混在一起读。发布前建议先补齐关键来源，并把“Goal 是验收条件”这个好观点从产品事实里剥离出来，写成作者的使用框架。

## 问题列表

### 🔴 必须修改（影响准确性或逻辑）

1. **开头事实段，第 18 行** “`codex-cli 0.133.0` 里 `goals` 已经是 stable feature”“OpenAI 在 2026-05-21 的 Codex changelog 里把 Goal mode 从 experimental 状态拿出来”“Codex app、IDE extension 和 CLI 都能用”都是关键产品事实，但正文没有给 changelog 链接，也没有说明本机确认方式。→ 建议：补 OpenAI changelog / 官方 commands 文档链接；`codex-cli 0.133.0` 如果保留，给出可复现来源（如 `codex --version` + `/goal` 命令输出）或删掉具体版本，改成“我在当前 CLI 版本里确认 `/goal` 可用”。

2. **“Goal 解决的是哪种尴尬”，第 32 行** “Codex 有一个更高优先级的靶子：当前 Goal”把产品行为写成了优先级机制，但公开文档通常只描述 persistent objective / thread-level state，并不等于公开了调度优先级。这个表述会让读者以为 Goal 在系统层面一定压过后续消息。→ 建议：降级为可观察语义，例如“Codex 会持续看到一个独立于普通聊天内容的当前目标”或“当前 Goal 会比散落在历史消息里的约束更显眼”。

3. **“我会怎么写 `/goal`”，第 67 行** “官方 app 命令文档也建议先用 `/plan` 把任务 shape 出来，再把收敛后的目标设置成 Goal”属于官方建议的转述，但没有来源；如果官方原文只是介绍 `/plan` 与 `/goal`，这里可能把作者方法写成官方推荐。→ 建议：要么补官方 app commands 文档链接并贴近原文措辞，要么改成“我更推荐先用 `/plan`……”，明确这是作者实践。

4. **“它和 Ralph Loop 像不像”，第 89-104 行及对比表** 这里同时涉及 Ralph Loop、Claude Code `/goal`、Claude Code `/loop` 的能力和触发/停止机制，但只有 Claude `/goal` 有链接，Ralph Loop 和 `/loop` 没有来源。尤其是“Anthropic verified”“Stop hook 拦截退出后重放 prompt”“`/loop` 时间间隔触发”“small fast model 检查 completion condition”都属于必须核查的产品能力。→ 建议：给 Ralph Loop 插件页 / GitHub README、Claude `/loop` 文档、Claude `/goal` 文档分别加链接；无法确认的表格项不要写成确定机制，改成“公开文档描述为……”。

5. **全文核心定义，第 34 行、第 172-174 行** “Goal 是给 agent 的验收条件”“把它当一张验收单”是文章最有力的判断，但也容易把 Goal 的产品语义收窄。官方语义更接近 persistent objective，验收条件是好 Goal 的写法，不一定是 Goal 本身。→ 建议：把定义改成“我建议把 Goal 写成验收条件”或“Goal 最有价值的用法，是把目标写成验收单”。这样既保留观点，也不会误导读者以为 `/goal` 只接受验收标准。

### 🟡 建议修改（影响表述质量）

1. **“什么算一个好 Goal”，第 38 行** Follow Goals 的适用场景被列得很完整，但“实验、游戏、side project”对这篇工程读者的主线帮助不大，读者可能会误以为 Goal 是泛化的长跑工具。→ 建议：保留官方列表但马上收束到工程场景，如“对工程实践来说，最值得关注的是迁移、重构、部署重试和带验证闭环的前端实现”。

2. **“什么算一个好 Goal”，第 40 行** “如果任务可以一句话做完，别开 Goal”判断过硬。一个任务能否一句话描述，和它是否需要跨 turn、验证闭环并不是一回事；“修完 CI 直到通过”一句话就能说完，但仍可能适合 Goal。→ 建议：改成“如果任务一轮就能完成，或没有结束标准，别开 Goal”。

3. **“什么算一个好 Goal”，第 53 行** “有用一百倍”是口语化夸张，问题不大，但这里正在建立判断框架，夸张会削弱可信度。→ 建议：改成更具体的收益，比如“能显著减少 Codex 把局部完成当整体完成的机会”。

4. **“我会用它替代什么”，第 136-140 行** 三类替代对象说得对，但第三类“让 Codex 沿着 Goal 继续推进，比每轮都问‘继续’更清楚”略像产品承诺。Goal 是否自动继续、如何跨 turn 继续，取决于具体客户端和当前会话机制。→ 建议：改成“在需要继续推进时，当前 Goal 能让‘继续’指向同一套验收条件”，避免暗示它总会自动接管下一步。

5. **“三个可以直接改的模板”，第 153 行** “pause after three distinct failed approaches with evidence”很好，但前文没有解释“失败几次后停”这个停止条件为什么重要。→ 建议：在“Goal 的效果取决于验证闭环”里加一句：“长任务还要写失败预算，不然 agent 会把时间花在低质量重试上。”这样模板里的三次失败就不是突然出现。

6. **语言规范，标题与第 34 行** 标题和核心句都用了“不是……而是……”句式，按写作指南属于高风险模板。这里标题是具体对比，不是空泛拔高，可以保留；但正文第 34 行再重复一次，会显得像金句堆叠。→ 建议：保留标题，正文改成“我会把 Goal 当成 agent 的验收条件，而不是鼓励语。”。

### 🟢 可选优化（锦上添花）

1. **开头第 12-20 行** 开头问题意识很清楚，但“新出了 Goal”对稍晚读到文章的人会过期。→ 建议：改成“Codex 的 Goal 从实验功能转成稳定功能后……”并接具体日期来源，时效更稳。

2. **第 44-51 行的好 Goal 示例** 示例很完整，但“每完成一个 section 跑一次 `pnpm test`”对纯首页 CSS 改造可能不如截图验证贴切。→ 建议：把测试命令换成更真实的组合，例如 `pnpm test` + `pnpm build`，或说明“如果这个项目有对应测试”。

3. **第 93-104 行对比段** 对比表有价值，但现在“下一轮靠什么触发”容易让读者以为四个工具处在同一抽象层。→ 建议：表格前加一句限制：“下面只按公开文档里的用户可见行为对比，不推断底层实现。”这能化解不少事实风险。

4. **结尾第 166-174 行** 结尾落点准，但“让我不舒服”这个情绪可以再具体一点。→ 建议：写成“它逼我把原本可以边做边想的验收标准提前写出来”，更贴合全文的工程判断。

## 亮点

文章最值得保留的是“Goal 不是更长 prompt，而是把完成条件从聊天历史里拎出来”这个角度。它比单纯介绍 `/goal pause/resume/clear` 更有读者价值。

好的 Goal 示例写得具体，包含范围、验证命令、停止条件和阻塞处理，能直接服务目标读者。尤其是修 CI 模板里的“三次不同失败路径后暂停并给证据”，比常见的“直到修好”更诚实，也更符合长期 agent 任务的真实风险。
